# Synthetic evaluation data

## Source and licensing
All data is produced by this repository's own generator (`money_trail.generation`) from a seed and a configuration
file. It contains no real, public or third-party records, so no external license or attribution applies. No AMLSim
adapter is implemented and nothing here claims AMLSim compatibility; the CSV pipeline loads whatever the dataset
config maps, and only the formats exercised by tests (the generator's own output and the shipped example mapping,
which has no data file) are verified.

## Generator
`money-trail generate --config examples/generator.example.json` writes, under `<output_dir>/<namespace>/`:

| File | Contents | Visible to the investigator |
|---|---|---|
| `accounts.csv`, `transactions.csv`, `alerts.csv` | public input data and seed alerts | yes (ingested) |
| `ingest_config.json` | ingestion mapping for the files above (editable defaults: strict, reject, batch 500) | n/a |
| `ground_truth.json` | evaluation labels | **no** |
| `dataset_manifest.json` | provenance: namespace, generator version, seed, counts, timestamps, SHA-256 of every file, limitations | n/a |

Reproducibility: the same configuration and seed produce byte-identical CSVs and ground truth, wherever they are
written (machine-specific output paths are not recorded). The manifest differs in `created_at`, and in the checksum of
`ingest_config.json` when the output locations differ (that file holds relative paths to them). Different seeds produce different data. The seed is mandatory; there is no implicit seeding.
The command refuses to write into a namespace directory that already has files unless `--overwrite` is given, and
overwriting touches only the generated file names. Nothing is generated by importing the package or running tests
against anything other than temporary directories.

Configuration (`examples/generator.example.json`): `namespace`, `seed`, `output_dir`, `ingest_output_dir`,
`currency {code, exponent}`, `amount_format` (`major` or `minor` in the CSV), `time_window {start, days}`,
`ordinary_activity {accounts, transactions, amount_minor{min,max}, channels}`, `id_prefixes`, `patterns[]`,
`seed_alerts`. Every value is validated; unknown keys are errors.

### Patterns
Each pattern entry gives a `count` of instances and its own ranges, all explicit:

* `circular`: a ring of `cycle_length` accounts; each hop passes `retention_bps` basis points of the previous amount
  (integer arithmetic) after a delay within `delay_seconds`, and the last hop returns to the first account.
* `pass_through`: a chain of `hops` transfers through intermediary accounts with the same retention and delay rules.
* `fan_in`: `sources` accounts each send one transfer to a single collector within the delay window.
* `fan_out`: one distributor sends one transfer to each of `recipients` accounts within the delay window.
* ordinary activity: uniform random transfers between distinct ordinary accounts, uniform random amounts and times.

`shared_account_fraction_percent` is the probability that a pattern slot reuses an ordinary account instead of a
fresh one. Random ordinary activity can incidentally resemble a pattern; only deliberate instances are labelled, and
`ground_truth.json` says so. All amounts are uniform within their ranges, which is not a realistic distribution.
Account and transaction identifiers are assigned after shuffling and time-sorting, so identifier order reveals nothing
about pattern membership (tested).

### Seed alerts
`seed_alerts` attaches a configured number of alerts to pattern transactions and a configured number to ordinary
transactions, in shuffled order, with the same `alert_type` and `severity` and `source = "seed"`. Alerts therefore
look alike and are noisy by design; their content carries no pattern information.

## Ground truth
`ground_truth.json` lists, per instance: `pattern_id`, `type`, `account_ids`, ordered `transaction_ids`, and `roles`
(cycle accounts, origin/mules/destination, collector/sources, distributor/recipients), all in the canonical
namespaced form stored in the graph, plus the full generator configuration and seed. It is for later evaluation.

Separation, enforced and tested:

1. The ingestion pipeline never opens `ground_truth.json`; the ingest config does not mention it.
2. The graph schema rejects unknown properties, and tests assert that every property key in the graph is a schema
   property, that no string value contains a pattern id or pattern vocabulary, and that the only relationship types
   present are `SENT`, `RECEIVED_BY` and `FLAGS`.
3. No label is stored on any node or edge, so ordinary queries cannot retrieve one; tests serialize the output of the
   context, activity and trace queries for pattern members and assert no labels appear.
4. The manifest omits pattern and seed-alert configuration (listed under `configuration_redacted_sections`) and
   does not summarize ground-truth contents.

The separation is a property of this repository's code paths, not of the filesystem: anyone (or any later agent)
given access to the dataset directory can read `ground_truth.json`. Later phases must keep it out of the agent's
accessible context.
